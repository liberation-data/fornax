Fornax runs each engine in-process, through Java's FFM API. These figures measure what that costs:
- **Against the engine's own tool:** the same engine, at the same pinned commit and backend, run through its own
  command-line tool on the same model files and settings.
- **Against ComfyUI, for songs:** what many people run today.

Every figure has the command that produced it under its table. The harness is
[`fornax-bench`](https://github.com/liberation-data/fornax/tree/main/fornax-bench), and one side runs at a time, so the
two never share the GPU.

**Machine** ({data.date}): {data.machine.cpu}, with {Math.round(data.machine.memoryBytes / 2 ** 30)} GB of memory
the OS can use (128 GB unified); {data.machine.os}; {data.machine.vulkanDriver}, Vulkan; Java {data.machine.java}.
Engines: llama.cpp <code>{data.machine['llama.cpp']}</code>, stable-diffusion.cpp <code>{data.machine['stable-diffusion.cpp']}</code>.

## Chat

<BenchTable id="chat" />

Through Fornax, llama.cpp runs as fast as it does in its own benchmark: the first token arrives at the same time, and
generation is within 2% of it. Fornax's peak memory is a little higher because the model loads with a 4096-token
context, where llama-bench sizes its own to the test.

## Serving many clients

<BenchTable id="serving" />

With 4 slots, `fornax server --parallel 4` keeps pace with llama-server's own `-np 4` at every load: within 3% on
throughput, and no longer a wait for the first token. Against one slot (`--parallel 1`, the default, where requests take
turns), four clients get 2.8 times the tokens a second between them, and wait at most 0.7 s for their first token
(95th percentile) instead of 11.5 s. Past the slots (8 clients) both servers queue the rest, so throughput stays where 4
left it and the wait grows. The three extra slots cost about 0.9 GB here: their KV cache, 3 × 2048 tokens.

[Isolated](/docs/guides/isolation/) (`FORNAX_ISOLATION=process`), the model and its slots run in a worker process, and
the batching works there as it does in-process: the same throughput and the same 95th-percentile wait at every load.
At 4 clients the median wait for the first token was 0.66 s, against 0.35 s in-process and 0.68 s for llama-server.

## Running them yourself

Build the reference tools from the same sources as Fornax, with the same backend. `native/build.sh` checks each engine
out at its pin in `native/engines.properties` under `engines-src/`, with Fornax's patches in `native/patches` applied,
and needs the same toolchain (for Vulkan: the Vulkan headers, `glslc` and SPIRV-Headers; see
[Choosing a GPU backend](/docs/guides/gpu-backends/#vulkan)). Build `llama-bench` and `sd-cli` from those checkouts,
then run the benchmarks:

```sh
native/build.sh vulkan llama sd
cmake -S engines-src/llama.cpp -B engines-src/llama.cpp/build-bench -G Ninja -DCMAKE_BUILD_TYPE=Release -DGGML_VULKAN=ON
cmake --build engines-src/llama.cpp/build-bench --target llama-bench llama-server
cmake -S engines-src/stable-diffusion.cpp -B engines-src/stable-diffusion.cpp/build-cli -G Ninja -DCMAKE_BUILD_TYPE=Release \
    -DSD_VULKAN=ON -DSD_BUILD_EXAMPLES=ON
cmake --build engines-src/stable-diffusion.cpp/build-cli --target sd-cli
./gradlew :fornax-bench:benchmarks --args='out/benchmarks chat image serving' \
    -Pllama.bench=$PWD/engines-src/llama.cpp/build-bench/bin/llama-bench \
    -Pllama.server=$PWD/engines-src/llama.cpp/build-bench/bin/llama-server \
    -Psd.cli=$PWD/engines-src/stable-diffusion.cpp/build-cli/bin/sd-cli
./gradlew :fornax-bench:bench --args='out/bench acestep yue2'      # with ComfyUI on 127.0.0.1:8188
```

Each run writes `results.json`, with the machine and the command behind every row, and `results.md`.
